Fraud detection with LLMs: signals, safeguards, and human review

Use language models to add context to a risk workflow—not to make unreviewable decisions.

Fraud teams already work with structured signals such as transaction velocity, device history, and account age. LLMs can help make unstructured evidence—merchant text, case notes, or customer-submitted narratives—more searchable and consistently categorized. Data engineering moves this evidence through secure, observable pipelines; data science evaluates whether it adds signal; machine learning engineering integrates it into a monitored workflow. LLM features remain one source of evidence alongside conventional detection systems.

Put the LLM in a bounded role

Have the model return a constrained schema: a small set of supported signal labels, confidence, and a short evidence reference. Validate the response, retain the source and model version, and ensure confidence is calibrated before it affects downstream ranking. Build data quality checks into ingestion, store prompt/model versions, and provide safe retries and fallbacks. Avoid sending unnecessary personal data, and do not allow arbitrary model-generated prose to trigger an adverse action.

  • Preserve the existing model score and policy rules as the baseline.
  • Measure whether language-derived signals improve recall at an acceptable review volume.
  • Route ambiguous or high-impact cases to trained human investigators.
  • Monitor drift, extraction failures, subgroup performance, and analyst overrides.

A transparent review-routing example

This compact Python example uses synthetic records and pre-extracted LLM signals. It caps the contribution of the language signal and only flags a case for human review; it does not approve or decline a transaction.

Python

transactions = [
    {"id": "tx-201", "base_risk": 0.82,
     "llm_signal": "account_takeover", "confidence": 0.92},
    {"id": "tx-202", "base_risk": 0.69,
     "llm_signal": "none", "confidence": 0.98},
]

def route_for_review(transaction):
    supported = transaction["llm_signal"] == "account_takeover"
    llm_adjustment = min(0.10, transaction["confidence"] * 0.10) if supported else 0.0
    combined_risk = min(1.0, transaction["base_risk"] + llm_adjustment)
    route = "human_review" if combined_risk >= 0.80 else "standard_queue"
    return combined_risk, route

for transaction in transactions:
    score, route = route_for_review(transaction)
    print(f'{transaction["id"]}: risk={score:.2f}, route={route}')

Output

tx-201: risk=0.91, route=human_review
tx-202: risk=0.69, route=standard_queue

The language-derived signal adds at most 0.10 to the synthetic baseline score, and the result only changes the review route. These illustrative numbers are not trained model outputs or recommended production thresholds. In a real system, the contribution, threshold, and confidence calibration must be selected using representative historical data and operational costs.

Measure impact before expanding the role

Evaluate on a time-based holdout to reflect changing fraud patterns and avoid future information leaking into training. Compare baseline and augmented systems on precision-recall metrics, investigator workload, time-to-review, and confirmed loss. Audit performance across relevant customer and transaction slices, and use a controlled rollout with a clear fallback when the LLM is unavailable or returns invalid output. Operational monitoring should cover data freshness, extraction errors, model and prompt versions, drift, latency, and cost.

Bottom line: use LLMs to surface and organize contextual clues. Keep high-impact decisions governed by validated models, explicit policy, and accountable human review.
