From messy text to useful features: a practical LLM pattern

Use language models to structure context—not to skip validation, domain knowledge, or careful evaluation.

Transaction data often arrives with a useful signal trapped in text: a merchant descriptor, support note, or short purchase memo. An LLM can map that messy language into a small, typed schema that a conventional model can consume. Think of it as an extraction stage, not an oracle. Data science defines which signals matter and how to measure them; data engineering makes the extraction repeatable; machine learning engineering integrates the validated features into a dependable model workflow.

Start with a narrow feature contract

Ask for fields that have a clear downstream purpose, such as a broad merchant category or purchase context. Define allowed values, require structured output, and validate every response before it enters a training table. In the data pipeline, retain source IDs, timestamps, extraction status, and model or prompt version so outputs can be traced, retried, and audited. For larger workloads, batch requests, handle rate limits, and make writes idempotent.

For sensitive data, minimize what is sent to the model, remove direct identifiers, and use an approved deployment. Treat missing, malformed, or low-confidence extraction as missing data; never silently turn an invalid response into a trustworthy-looking feature. Track parse failures, latency, cost, and feature freshness alongside model quality.

Keep preprocessing on the right side of the split

Here is a small, dependency-free example. The LLM extraction is represented by already-validated structured responses; this code then makes a chronological train/test split and learns the category vocabulary from training data only.

Python

from datetime import date

rows = [
    {"day": "2025-01-01", "amount": 18.50, "category": "dining", "recurring": False},
    {"day": "2025-01-02", "amount": 42.00, "category": "grocery", "recurring": False},
    {"day": "2025-01-03", "amount": 9.25, "category": "dining", "recurring": True},
    {"day": "2025-01-04", "amount": 63.00, "category": "grocery", "recurring": False},
    {"day": "2025-01-05", "amount": 120.00, "category": "travel", "recurring": False},
    {"day": "2025-01-06", "amount": 15.00, "category": "dining", "recurring": False},
]

rows.sort(key=lambda row: date.fromisoformat(row["day"]))
cut = int(len(rows) * 0.67)
train, test = rows[:cut], rows[cut:]
known_categories = {row["category"] for row in train}

def make_features(row):
    category = row["category"] if row["category"] in known_categories else "other"
    return {
        "amount": row["amount"],
        "is_recurring": int(row["recurring"]),
        f"category_{category}": 1,
    }

print(f"train={len(train)}, test={len(test)}")
print(f"training categories={sorted(known_categories)}")
print(make_features(test[0]))

Output

train=4, test=2
training categories=['dining', 'grocery']
{'amount': 120.0, 'is_recurring': 0, 'category_other': 1}

The unseen travel value is mapped to an explicit fallback instead of teaching the encoder about test data. In a production pipeline, fit the encoder and any imputation or scaling steps only on the training fold, then reuse those fitted transformations unchanged on validation and test data. For a non-temporal use case, use a split that reflects the deployment setting and prevents entity or label leakage.

Evaluate the added signal, not the novelty

Compare against a baseline that uses the original structured fields. Use the same split for both models and check metrics aligned to the decision—such as precision-recall performance when positive cases are rare. Review errors by merchant, time period, and customer segment; extraction quality and downstream model quality are separate things to measure. In a production MLOps workflow, version the feature contract and extraction prompt, validate data distributions, and monitor for drift or upstream pipeline failures.

Practical rule: add an LLM-derived feature only when an ablation shows that it provides stable, incremental value and the feature can be monitored, reproduced, and governed.
